# 验证范围

验证平台为 Windows x86-64、MinGW-w64 GCC 15.1.0、xmake 2.9.6。
Debug/Release 均使用 C11；测试检查不依赖 `assert`，Release 仍执行测试动作。
以下记录只覆盖所列组合和输入，不表示完整 C11、其他平台或全部 TinyCC 功能通过。

2026-10-20，`python tests/verify.py --mode debug` 和 `--mode release` 均完整通过：
各十六组根 C 回归、六组编译集成检查（含 `scope` 和新增 `functions` 语义样例和 120 个 TinyCC 输入差分）、
24 对阶段产物一致性及两种构建方式下各 39 项 OpenOICC 回归。21 个语料排除项见下文。
两种模式均生成 `verification.json` 成功记录。
本阶段全量入口未包含可选 `PP_DEBUG` 调试输出运行验证。

## 根 C 回归

`xmake test -P . -v` 执行十六组：

- `runtime_dispatch_test`：七个接力接口的结果、访问撤销和席位耗尽。
- `runtime_robustness_test`：原 NEOioic 的队列随机操作、模式、引用、共享祖先、
  构造失败、OID 边界、动态/外部存储和部分关闭。
- `source_test`：未对齐消息、长名称/长度、EOB、257 层缓冲、真实文件名、借用
  stdin、拥有句柄、共享打开、对象隔离、1000 次 OID 回收及部分关闭重试。
- `source_fault_test`：构造区与两队列分配失败、缓冲失败保留句柄所有权、文件名
  分配失败保留原名，并记录释放数量。
- `session_test`：64 轮交替双会话编译、宏隔离、嵌套展开/拼接/字符串化、
  逐文件 `__COUNTER__` 重置、浮点常量/运算的交替编译和重定位后实际调用、带行号的诊断、
  未定义标签错误后的栈/token 链接清理、错误后新会话编译和句柄计数。
- `session_fault_test`：三处源缓冲失败，核对 `longjmp` 后资源、访问记录及后续编译。
- `tokens_test`：未对齐消息、2000 个名称及索引扩容、驻留稳定性、对象隔离、对齐、
  跨对象指针拒绝、尺寸溢出、宏流增长/缩小/释放、共享打开和 reset/关闭后的重新编号。
- `tokens_fault_test`：索引首次分配、扩容和符号块分配失败，不发布 token；宏流扩展
  分配失败保留原内容；最终释放数量与启动时一致。
- `preprocessor_test`：未对齐消息、257 层宏流、恢复流位置与源行号、三种流释放策略、
  失败消息不修改栈、token/值与源游标隔离、工作区及常量载荷的宿主对齐、字符分类、
  reset 清零并保持借用地址、共享打开、部分关闭重试、末次关闭后的拒绝借用和再次打开。
- `expressions_test`：独立值栈/常用类型、宿主对齐、数组两端和哨兵、未对齐/短消息、
  共享打开、reset 保持地址并清除符号引用、部分关闭、关闭后拒绝借用及再次打开。
- `symbols_test`：600 个普通符号记录的增长、对齐、内容保持、LIFO 复用、
  global/local/宏定义/global label/local label 五类栈、作用域边界、copy/move 顺序、
  未对齐消息、对象隔离、reset、共享打开、关闭后拒绝分配、再次打开及部分关闭重试。
- `symbols_fault_test`：构造区/两队列分配失败，首块及后续各块分配失败保留原内容和池、
  push 分配失败不发布栈节点，检查 VO 记录撤销及最终分配/释放数量。
- `scopes_test`：258 层作用域帧继承、逆序出栈和复用、对象隔离、非法栈顶/跨对象/循环
  出栈拒绝、未对齐/短消息、reset、共享打开、部分关闭、关闭后拒绝借用及再次打开。
- `scopes_fault_test`：构造区/两队列及各层帧分配失败保留原状态，复用不再分配，
  检查 VO 记录及最终分配/释放数量与测试开始时一致。
- `functions_test`：独立函数工作区、BEGIN 清除旧缓存、临时槽首次匹配/占用/对齐、
  八项缓存满后继续分配、局部栈偏移不回退、零尺寸、偏移溢出及无效消息保留原状态，
  reset、共享打开、部分关闭、关闭后拒绝借用及再次打开。
- `directory_test`：Windows 空目录、缺失目录、文件作为目录、含空格名称、回调失败
  的 1000 次枚举与句柄清理。

宿主故障注入依赖 GNU ld `--wrap`；不是 NeoCC 生产开关。
`session_fault_test` 另注入七个对象的构造失败及预处理/表达式两个工作区分配失败、宏流和标识符两个 arena 的分配失败，检查输入清理、token
对象 VO 记录撤销，以及之后新会话的编译；原有会话错误计数累积语义保持不变。
另注入八处工作字符串与 token 索引扩容失败，以及三处语义符号分配失败，检查池、五类栈头、
作用域层级归零和新会话恢复编译。另触发真实值栈耗尽诊断，检查表达式数组、栈顶、
常用类型引用和 VO 记录在错误后清空，再创建新会话编译。
另在五处根/嵌套作用域帧分配失败后检查 active/available、作用域入口、清理/goto 链头
清空，覆盖已建立 cleanup 和前向 goto 记录的错误路径及新会话恢复。
另在普通和 `-gdwarf-5` 配置下，在变参/大结构体返回/VLA 函数内产生临时槽与返回跳转链后，
触发未声明标识符诊断；回调先确认工作区非空，收尾后检查类型/名称、偏移、跳转链和缓存
清空以及新会话恢复。构造/工作区故障现在共九处（七个图和两个独立工作区）。
检查工作区归零、VO 记录清空及整体分配/释放数量；旧编译器的致命分配器通过测试专用
可替换分配器绕过注入，避免把 exit 当作可恢复错误。测试分配器带独立内存头，
同时检查选项解析和搜索路径列表的分配域边界，发现跨分配器释放会直接失败。

## 纯 C 与 NEOioic 编译差分

`tests/regression.py` 包含六组集成检查：

- 自有 C11 程序在 GCC、TinyCC 基线和 NeoCC 下编译运行，比较输出与退出码；覆盖
  类型、嵌套作用域/标签/局部 extern、结构体/浮点/可变参数 ABI、VLA、对齐、指针及
  跨文件重定位。作用域样例另覆盖 cleanup 的前向/后向 goto、return、VLA 与
  for/switch 的 break/continue、语句表达式清理。函数样例覆盖大结构体返回、十个结构体
  实参、递归/间接/内联调用、变参浮点、旧式参数、函数指针返回、VLA 参数和 `__func__`。
- 对同一输入比较 TinyCC/NeoCC 预处理文本，以及无调试信息、`-g` 和 `-gdwarf-5`
  三种选项下的 ELF 目标字节，包含预处理、语义、作用域及函数样例。
- 包含链与 `#line` 诊断、缺失文件、输出失败，比较错误退出和诊断内容。
- NeoCC 编译并实际运行 NEOioic 分派、健壮性、菱形继承和本项目源对象/token 对象/预处理对象/符号对象/表达式对象/作用域对象/函数对象/目录测试。
  NEOioic 故障注入通过测试翻译单元的编译期函数替换实现，真实分配器另编译；
  不要求 NeoCC PE 链接器支持 GNU `--wrap`。
- TinyCC `tests/tests2` 的 120 个输入逐项差分；21 个平台特定或需要本阶段未启用运行库的输入明确排除，
  完整名单和原因保留在脚本及运行后的 `regression/results.json`。

语料差分同时比较结果和退出码；共同失败只能证明未产生迁移差异，不能作为其 C
功能正确的证据。`34_array_assignment` 为上游已排除的非标准扩展；i386/ARM/RISC-V、
pthread/TLS、多 DLL 边界检查与回溯、ELF 动态链接案例未纳入当前覆盖。
没有把这些案例改成宽松的“通过”。GCC/新建程序提供额外正向结果依据。

## 自举及构造再生

`tests/bootstrap.py` 从 GCC 构建的第一阶段 NeoCC 开始，以普通 C 源码独立编译
CLI、宿主、源对象、所有当前后端/编译模块和 NEOioic，链接第二阶段；再用第二阶段
构建第三阶段。各阶段还重新编译运行库和 OpenOICC。

第二/三阶段的 22 个 NeoCC/NEOioic 目标文件、NeoCC 可执行文件和 OpenOICC
可执行文件共 24 对逐字节一致；`libtcc1.a`、`runmain.o` 也逐阶段比较。
不启用调试路径或时间戳等可变字段，不以修改预期哈希掩盖差异。
`bootstrap/results.json` 记录本次产物 SHA-256，不提交本机绝对路径。

第二、第三阶段 OpenOICC 各在构建目录副本中预览、显式再生两次，七个对象构造区均无变化，
再用该阶段 NeoCC 编译并运行源对象、token 对象、预处理对象、符号对象、表达式对象、作用域对象及函数对象测试；阶段工具
还编译运行 C11 语义样例、作用域/标签和函数样例。
这证明当前源码/目标组合的阶段稳定性，不代表整个编译器对象化完成。

`tests/verify.py` 还对 GCC 构建和第三阶段 NeoCC 构建的 OpenOICC 分别运行全部
39 项集成回归，覆盖随机图、故障分配、布局、区外字节、幂等再生和再编译。
测试辅助 C 程序仍由 GCC 构建；不得把此结果描述为其所有辅助程序都由 NeoCC 编译。

## 不含 TinyCC 参考树的验证

`tests/independent.py --mode debug`（或 `release`）每次建立全新的仓库内源码副本，
不复制 `tinycc/`、现有产物或缓存。在副本中用 GCC/xmake 构建，执行十六组根回归，
再以 NeoCC 完成第二/三阶段编译、运行库重建、24 对输出比较和七个对象的构造再生。
两种模式的独立性结果位于 `build/independent/debug.json` 和 `release.json`。
完整验证入口包含该检查；独立性副本不运行需要参考语料的 TinyCC 差分。
它证明构建和运行不依赖参考树，不能证明全套对象化重写已经完成。
